# 播放器核心体验以候选真实链路作为发布门

## Status

Accepted

## Context

Aurorama 1.4.0 通过了大量 JVM、静态、构建和 merge/prep 门禁，但正式包 QA 没有实际执行视频播放、seek、续播、字幕、换集、切账号和跨设备音乐播放。用户在真实使用中发现多项严重播放体验问题，而且部分问题的相关代码从 1.3.0 起就存在。这说明测试数量、控制面 PASS 和 fake callback 覆盖不能替代真实候选链路。

## Decision

1. 播放器核心进入候选发布前，必须在精确签名候选包上执行 `docs/TEST_PLAN.md` §8 的 `PLAYER_CORE_RELEASE_MATRIX`；任一行 `NOT_RUN` 都不得以 `PASS_WITH_GAPS` 放行。
2. 用户报告为 1.4.0 回归的播放器问题，必须用同一设备、同一片源、同一账号和同一操作做 1.3.0/1.4.0 A/B；没有直接证据时只能标 `REGRESSION_SUSPECTED` 或 `KNOWN_EXISTING`。
3. 恢复 1.3.0 行为只允许路径级、行为级的最小补丁，禁止整文件、整模块或整提交覆盖 1.4.0。任何恢复必须列出保留的 1.4.0 新能力并通过对象与回归审计。
4. 播放器核心存在未关闭的 P1，或高频阻断主流程的 P2 时不得发布；P0/P1/P2 不得由“测试数量多”“控制面 PASS”或“用户后续发现”冲抵。
5. 日常使用手机可以作为用户协助的真实入口验证设备，但不得修改系统底层设置、开发者选项、网络策略、权限数据库、代理或设备配置。
6. 同一播放器故障簇最多经历一轮实现、一次定向复审和一次必要补丁；第二轮仍存在同一 P1 时停止打补丁，重新设计状态模型。

## Considered Options

- 只继续增加单元测试：拒绝。测试层级错误时，增加数量不会产生真实用户链路证据。
- 整版本回退到 1.3.0：拒绝。会丢失 1.4.0 的数据和功能。
- 用 `PASS_WITH_GAPS` 接受未执行的核心链路：拒绝。这正是 1.4.0 发布门失效的原因。

## Consequences

播放器发布会更慢，部分无法稳定修复的 1.4.0 子能力可能需要经用户确认后暂时降级；换取的是可复核的真实用户链路、清晰的版本归属和不再积累“全绿但不可用”的证据债。
