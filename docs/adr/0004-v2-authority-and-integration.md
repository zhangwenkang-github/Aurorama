# V2 权威文档、决策权与集成交付模型

**Status**: accepted (2026-11-02)

V2 使用 `V2_PLAN` 作为需求与交付账本，`PROJECT_RULES`、`LESSONS`、`TASKS`、`DECISIONS` 和 `docs/adr/` 各自承担单一职责。产品范围、用户可见行为、UX、数据兼容、服务器写边界和外部发布由用户拍板；内部可逆实现由团队留痕决定。任务完成要求独立 QA、merge-prep、进入 `codex/v2-integration` 并通过集成态门禁，外部 push/tag/Release 仍单独授权。

**Why**: 现有规范、进度和教训分散在超大任务线、聊天和记忆里，导致冷启动重复通读、决定丢失和孤儿分支。把需求、规则、任务、决策分开，并增加持续集成门，可同时降低上下文成本与“写完忘合并”的风险。

**Consequences**:

- 每次接力只读当前需求域白名单，但仍必须加载规则、教训索引、活跃任务和相关决策。
- 功能分支通过自身测试不是 `Done`；集成分支才是交付状态来源。
- 功能分支从当前批准集成目标的具体 SHA 创建，不得依赖其他功能分支；一日生命周期是目标，超期必须说明并做集成演练；分支存活期间每日或每次交接检查拓扑。
- 未发布分支的常规可逆 rebase / merge / cherry-pick 由独立 merge-prep 留痕执行、主责复核；历史重写、已发布分支、语义冲突或候选祖先异常必须交用户。
- G1 建立架构违规基线；每个任务禁止新增违规；发布门必须关闭全部未豁免违规，违规必须有稳定 ID、归属、豁免依据和关闭证据。
- 用户不需要承担内部实现细节，但不能跳过产品、UX、数据安全和发布决策。
- 外部 push/tag/Release 保持独立审批，集成分支不自动等于发布。

**Alternatives considered**:

- 继续把所有内容堆进 `PROJECT_PLAN` / 单一任务线：无法保持加载预算。
- 使用 `DECISIONS.md` 同时承担决策索引和全部 ADR：重复、失焦且难追溯。
- 功能分支自测后直接标 Done：重复历史孤儿分支问题。
- 允许自动 push 和发布：越过用户对远端与正式资产的明确授权。
