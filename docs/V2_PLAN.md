## 3. 2.0 定义与不可破坏结果

Aurorama 2.0 是正式 `2.0.0` 产品大版本，同时代表内部 V2 架构和研发流程代际升级。它不只是一个版本号、UI 改版或功能集合。

不可破坏结果：

- 从现有正式版升级时，不得丢失或破坏登录、已有下载、书签、阅读进度、歌单、播放进度、偏好设置和本地媒体库。
- 所有服务器写操作只针对用户指定的独立测试写入服务器；生产服务器继续只读。
- 原始需求中的条目默认进入候选范围，未经用户明确批准不得静默删除。
- 每条需求最终必须归类为 `MUST / SHOULD / LATER / OUT`；分类改变必须留痕。
- 2.0 文档的全部需求未完成归一前，不进入产品实现；需求门完成后仍需通过方案门和开发门。

## 9. 2.0 范围与旧债策略

外部原始需求中的所有条目默认进入候选范围。最终分类必须由用户确认：

- `MUST`：2.0 发布门必须完成。
- `SHOULD`：目标包含，发生范围冲突时由用户决定延期。
- `LATER`：明确不阻塞 2.0，但仍保留来源和后续入口。
- `OUT`：用户明确移出 2.0。

1.4.0 的已知遗留必须进入统一矩阵，状态为 `CLOSED / MERGED / EQUIVALENT / DEFERRED / RETIRED / ACCEPTED_RESIDUAL`。特别是历史搜索 P1、下载通知一致性、已接受 P3 和用户延期需求，不得因进入 2.0 而自动消失。

## 10. 分支、QA 与完成定义

- 任务分支：`codex/v2-<任务ID>-<简述>`。
- 集成分支：`codex/v2-integration`。
- 实现者只做 TDD、构建和最小边界自测，不自行开启独立 QA 或 merge-prep。
- 独立 QA 使用与实现者不同的全新代理，可在隔离测试环境通过真实 UI 点击、`adb` 文本取证、fixture 和自动化执行核心旅程。
- merge-prep 使用另一个独立角色，核对 target 漂移、白名单、source/final patch-id、目标态门禁和承诺祖先。
- `Done` 表示已进入集成分支并通过集成态门禁；外部 push、tag、GitHub Release 和正式资产上传必须另行获得用户授权。
- 任务分支在本地进入集成分支且不再需要后可删除；远端分支仅在用户批准 push 后按集成结果清理。
